1. Project Overview
Your team will design, build, and maintain a software application that contains an AI component, using
an AI coding agent under human supervision. The project applies the full software engineering lifecycle
taught in this course: you will specify requirements in machine-readable form, produce architecture
artifacts that constrain what the coding agent may and may not do, govern the agent's code generation
and verification, and demonstrate that you can review, debug, and maintain AI-generated code.
Your application is your own choice — it must contain at least one genuine AI component (an LLM-
powered feature, a retrieval/augmentation pipeline, an AI-assisted decision path, etc.) and at least one
safety-relevant boundary where the AI's output must be constrained by deterministic code. The
reference implementation shown in lectures (VHIS) is a pattern to follow, not a project to extend.

3. Deliverables
D1 — Requirements (machine-readable)
Produce a machine-readable product requirements document and a consolidated requirements
registry, both in YAML, under `./docs/req/` where `.` is the project root.

•   `docs/req/requirements.yaml` — every requirement as an entry with an ID, type, statement, and a
    machine-checkable fit criterion, plus priority. Types cover functional behavior, invariants (non-
    negotiable rules with zero-tolerance fit criteria), quality attributes, performance, cost, governance,
    and security. Non-functional requirements are expressed as metric + threshold + verification.
    Prioritization uses MoSCoW, and states the tradeoff explicitly. Requirements discovered through
    analysis of any existing system or repository are included and linked to their sources.
•   `docs/req/req-schema.json` — the schema used by CI in GitHub to validate the registry as a date.

D2 — Architecture Artifacts (all as markdown .md files)
Produce the architecture documentation as a single artifact per file in `./docs/architecture/`, with `.`
as the project root.
1. Architecture blueprint — the master constraint document that the Plan agent reads: scope,
    architectural drivers, system boundaries, components, authority boundaries (what is advisory vs
    authoritative), agent workflow, permissions, verification strategy, observability, and change policy.
2. Architecture Decision Record — the chosen architecture, the alternatives considered, the
    rationale, consequences, and conditions that would reopen the decision. It should also present the
    architectural design process. In addition, for your AI component, present your designed layered
    context structure that the AI receives on every turn (e.g., identity, standing constraints, retrieved
    knowledge, conversation history, resumable state, and the current task), the assembly pipeline
    (e.g., deduplicate, prioritize, budget, compact, assemble), the token-budget cap with its compaction
    threshold, and the policy for re-injecting critical constraints after compaction.
3. Invariant register — every invariant with its statement, source requirement ID, enforcing
    component, verification method, and an operational fallback if it is ever violated (a concrete action,
    not “fix the bug”).
4. Trace matrix — every requirement mapped to its enforcing component, its test/evidence, and its
    runtime monitor.
5. Memory/state design — what state survives across sessions, interruptions, and versions; write and
    retrieval policy; ownership; retention; privacy.
6. Permission model — file-level read/write rights for each AI coding agent’s role; default is no read,
    no write; every path is explicitly whitelisted.
7. Runtime policy catalog — what the system does when each degraded or failure path is triggered.
8. Candidate evaluation table — the comparison that justifies the chosen architecture.
9. [optional] Evaluation logbook — the accumulated evidence behind the architecture choices.
10. [optional] Risk list — assumptions that could become defects, with review triggers.
11. [optional] Option ledger — rejected architectural options and when they should be reconsidered.

•   `AGENTS.md` (at the project root directory) — the single entry point the coding agent reads. It
    declares the build target, the reading order for architecture artifacts, the code baseline, what is
    readable/modifiable/frozen, the module organization, the integration contracts between modules,
    and the verification requirements that the generated code must satisfy.

•   `docs/code-governance/structural-constraints.md` — module organization rules: each
    architectural element maps to exactly one module; new work extends the existing baseline, never
    replaces it; every module and function references the architecture decision and invariant it
    implements; authority boundaries.
•   `docs/code-governance/mcp-tool-manifest.md` — the tools the coding agent may call, and which

•   `.opencode/permissions.jsonc` — the project-level permission model in machine-readable form,

•   `.agent/rules.md` — the project covenant: abstraction limits, dependency constraints, test
    independence (at least one negative test per feature), the rule that changing safety-critical code
    requires an architecture decision and human approval, and context freshness (rules updated within
    one sprint of a requirements change).

D4 — Verification Governance (as markdown .md files)
Produce the verification rules that the verification agent applies, and the QA records the team maintains:

•   `docs/code-governance/verification-constraints.md` — every fit criterion has at least one test;
    every invariant has at least one test that fails when the invariant is violated; every test references the
    requirement or invariant it verifies; every new round of work runs all previous rounds' test suites with
    zero regressions.
•   Verification is three-tiered: structural (imports, module boundaries, permissions, architectural
    fitness functions), regression (all prior suites pass), and behavioral (quality thresholds such as
    faithfulness/relevance scores, zero safety escapes).
•   `docs/review-memo.md` — a review memo per pull request, covering spec alignment, architecture
    alignment, code and test quality, and operational metadata, with security and efficiency checked
    throughout, ending in a verdict of APPROVE, CHANGES REQUIRED, or REJECT.
•   `docs/debt-register.md` — technical debt tracked across the AI-era categories: prompt rot,
    hallucinated dependencies, untouchable code, hidden dependencies, agent-induced bloat,
    evaluation debt, guardrail debt, and human/cognitive debt.
•   `docs/bug-diary.md` — a diary entry per significant bug: symptom, reproduction, classification,
    root cause, fix, and which invariant gap it exposed.

6. Blocking-Gate Requirements (D7)
The CI/CD pipeline must implement the following blocking gates.
1. Test approval gate — no code change merges unless the tests for the change were approved before
   implementation began.
2. Static analysis gates — lint, type-checking, and dependency checks run on every commit; contract,
   security, API-surface, and permission checks run on any pull request touching safety-relevant paths.
3. Schema gate — the requirements registry validates against its JSON schema.
4. Semantic evaluation gate — for any prompt or model change, the pipeline replays a fixed
   evaluation set against quality thresholds before the change can reach production; if a threshold
   fails, the change is blocked and reported.
5. Regression gate — every change runs the full prior test suites; any regression blocks the merge.
6. AI-use log gate — a pull request that changes code or prompts without updating the AI-use log is
   blocked.

 Branch protection: Branch protection must require passing CI, and changes to safety-critical paths
 must require human review with an accompanying architecture decision.

FILE: architecture-blueprint.md
# Architecture blueprint

Decision: leo accepted application composition over TradingAgents v0.4.0. Authoritative design: ADR-001. Scope: one local operator, US equities, English reports, market/news analysts and the complete downstream upstream graph. The application supports research, evidence replay, paper execution and controlled context experiments.

## Drivers and boundaries

The strongest driver is a visible authority boundary between probabilistic research and deterministic portfolio state. Reproducibility requires freezing material data without claiming to recreate stochastic generation. Maintainability requires keeping the upstream graph and tests intact. Cost evaluation requires the same model and graph for both arms, so replacing expensive agents would invalidate this experiment.

The operator invokes a CLI. A ResearchRunner constructs the real graph, supplies context and records callbacks. The EvidenceTradingGraph subclass owns data seams that callbacks alone cannot see, including instrument identity and returns reads. Tool adapters supply fixed corpus data during controlled reruns. Research produces a terminal state and evidence package. It never executes a trade.

```mermaid
flowchart LR
  Operator --> CLI
  CLI --> Runner[ResearchRunner]
  Runner --> Context[Context and request budget]
  Context --> Graph[TradingAgentsGraph]
  Corpus[Frozen evidence] --> Graph
  Graph --> Pack[Evidence package]
  Pack --> Replay[Offline replay]
  Pack --> Pending[Pending proposal]
  Operator --> Review[Exact-term approval]
  Review --> Pending
  Pending --> Policy[Deterministic current-ledger checks]
  Policy --> Ledger[Atomic paper ledger]
```

## Component ownership

| Element | Owning module | Contract |
|---|---|---|
| Structured records | `models.py` | Explicit persisted fields, normalized statuses and proposal version |
| Settings | `config.py` | Home paths and authoritative teaching policy constants |
| Evidence recording and package IO | `evidence.py` | Capture actual calls, tool data and direct reads; reject incomplete packages |
| Real graph integration | `graph_adapter.py` | Preserve graph roles, freeze non-LLM inputs, derive evidence price |
| Context assembly | `context.py` | Preserve critical facts, remove redundant text only in compact mode |
| Request budget | `budget.py` | Prevent the next model request at the configured limit |
| Approval lifecycle | `review.py` | Exact-term approval, re-review on changed terms, idempotent execution |
| Portfolio policy | `policy.py` | Cash, total-position cap and no-short checks without an LLM |
| Persistent ledger | `storage.py` | SQLite proposal/position/transaction persistence |
| Replay | `replay.py` | Rebuild reports from captured state without creating a model client |
| Operator interface | `cli.py` | Research, review and replay commands |
| Report rendering | `report.py` | Evidence-derived identity header and inspectable Markdown/HTML output |
| Per-request context control | `eval/compact_delegate.py` | Uniform grounding, complete-input compaction and hard cap |
| Live evaluation | `eval/live.py` | Real graph runs and isolated semantic judgments |
| Release evidence validation | `eval/quality.py` | Current-source provenance and fixed quality thresholds |

The new modules reuse upstream public declarations rather than reimplement agent reasoning. Any additional frozen-corpus or evaluation modules remain application owned and do not change vendor routing.

## Authority and execution

Only the local operator can approve exact proposal terms. The model supplies a signal and reasoning. The quantity comes from the operator; the price comes from captured evidence. The deterministic policy uses current ledger state immediately before execution. A content fingerprint is appropriate here because approval must refer to exact terms; it is not a release version. SQLite records a single atomic transaction, and repeated execution returns the original result.

One research run executes sequentially within a process because upstream configuration has process-level state. Independent evaluation processes may run concurrently with separate homes. The ledger supports the single-operator CLI workflow; this release does not expose a concurrent network trading service.

## Verification and observation

Structural checks preserve import/module boundaries and governance records. Regression runs include the complete original upstream suite plus the extension tests. Behavioral verification evaluates exact safety examples and six frozen research cases. Events record context decisions, request counts, provider tokens, tool reads, terminal outcome and stop reason. A successful provider response is evidence of execution, not evidence of factual quality.

Change policy: new requirements update the registry, trace matrix, tests and affected ADR in the same change. Runtime context changes require fixed-set semantic replay and saved live comparison evidence. Failed or budget-stopped runs remain available and cannot become approved research. See the runtime policy catalog for operational actions.

## Release revision

ADR-004 adds a complete-input ceiling of 96,000 conservative units and a compaction trigger of 72,000. The request delegate measures the complete message sequence before each provider invocation, records the transformation, and stops if required content still exceeds the cap. Critical constraints and tool-call/result relationships survive compaction. Rejection remains terminal in the approval lifecycle. The release validator binds saved research and judgments to the current runtime source and checks each quality dimension separately.

# Memory and state design

Research memory and paper execution state have different owners. Upstream memory retains structured research decisions for reflection; the application captures exactly the memory used by a run. The paper ledger records approved transactions. A model-generated reflection cannot write the paper ledger.

The application home, selected by RESEARCH_DESK_HOME, contains the SQLite database and run directories. Every demonstration and evaluation uses a separate project-local home. SQLite stores proposals, cash, positions and transactions. Evidence files store manifest, material input, events, calls, provider usage and terminal state. A package can be transferred independently of the database for replay. Proposal approval refers to exact evidence and trade terms.

A completed run survives process exit through its evidence package. Interrupted or budget-stopped runs retain the terminal reason and collected calls. Replay reconstructs saved state. A controlled rerun creates a new run and refers to its source evidence. The evaluation command replaces the selected arm output directory, so the host runner archives earlier attempts and resumes completed cases. A reviewer must use a new output root when repeating the submitted experiment.

Memory retrieval applies the analysis cutoff to resolution/availability dates. Retrieval date is recorded separately because downloading a July release in August does not make its content available before July. Future-resolved lessons are excluded. Unknown availability is visible and unsuitable for strict historical claims. This rule concerns input provenance and does not certify investment validity.

The package schema starts at version1. Release names follow ordinary semantic versioning. Content fingerprints serve integrity and exact approval binding only. Changes to persisted contracts need an explicit migration or documented import path before claiming compatibility. No unsupported cross-version restoration is promised.

Retention: keep source fixtures, experiment evidence, decisions and full credential-scanned sessions through assessment; retain ledger demonstrations as reproducible fixtures. Credentials are never durable state. User-specific caches, environment files and Yahoo cookies are excluded from the submission and repository. Deleting a project home resets local paper state and must not delete the immutable submitted experiment evidence.

The teaching valuation convention re-marks the ticker under review at its captured evidence price. Other holdings use their stored average price, which is visible in ledger records. This is a declared local paper-account convention; a future mark-to-market portfolio service requires explicit per-position market marks.

# Permission model

The principle is no access until a role needs a path. The machine-readable permissions and effective OpenCode configuration must agree; a file named permissions.jsonc alone is not enforcement. The host keeps credentials outside agent-readable files and injects only the application's runtime environment.

| Role | Read | Write | Forbidden |
|---|---|---|---|
| Plan | AGENTS, Prompt, docs, public upstream source, src/test declarations | proposed plan documents | Application implementation, approvals, secrets |
| Build | Approved requirements/architecture/tests, src, test, pyproject | src/research_desk, approved test files, scoped package metadata | Human-owned rules/approval decisions, global config, upstream replacement |
| Verify | Source, tests, requirements, frozen fixtures, run evidence | verification outputs and proposed test changes | Granting approval, weakening requirements, editing source to force a result |
| Release | Final artifacts and local git state | package, workflow evidence, authorized project remote | Publishing credentials, real orders |
| leo | All project decisions and review evidence | Plans, ADRs, rules, concrete stage approvals | Falsifying raw sessions or measured results |

Runtime authority is separate from coding-agent permissions. The graph has market/news tools and model access. It has no review, execute or ledger tool. The local operator commands own approval and execution. This is a single-user workstation boundary, not a claim of production identity assurance.

Safety-relevant paths include policy.py, review.py, storage.py, config.py, model contracts, permission configuration and rule files. Changes need a reviewed ADR plus a corresponding approval record. Current fixes to total holdings, valid sells and exact approval binding are covered by ADR-002 and the approved AT-04/05 semantics.

FILE: src/research_desk/review.py
"""Proposal review state machine and simulated-ledger execution.

Flow: research produces a PENDING_REVIEW proposal. A trusted CLI operator
approves or rejects it. Execution re-evaluates the *current* ledger against the
deterministic policy before writing; the approval binds the exact proposal
version, so a changed proposal cannot ride an old approval. Re-executing an
already-simulated proposal is a no-op (idempotence).

No LLM path reaches this module: the research graph only ever writes a proposal
in PENDING_REVIEW, and only the CLI review/execute/ledger commands touch it.
"""

from __future__ import annotations

import uuid
from datetime import datetime, timezone

from .models import (
    ExecutionRecord,
    ProposalRecord,
    ProposalStatus,
    TransactionRecord,
    TransactionStatus,
    make_proposal_version,
    utcnow_iso,
)
from .policy import evaluate_buy, evaluate_sell

# Signals that map to a tradeable buy action; everything else is a sell or
# non-tradeable (Hold / REVIEW).
BUY_SIGNALS = {"Buy", "Overweight", "Strong Buy"}
SELL_SIGNALS = {"Sell", "Underweight", "Reduce"}


def _side_for_signal(signal: str) -> str:
    if signal in BUY_SIGNALS:
        return "buy"
    if signal in SELL_SIGNALS:
        return "sell"
    raise ReviewError(f"signal {signal!r} is not tradeable in v1 (Hold/REVIEW do not trade)")


class ReviewError(Exception):
    """Business rejection with a stable message; the ledger stays unchanged."""


def _proposal_content_version(proposal: ProposalRecord) -> str:
    """Fingerprint of the proposal's tradeable inputs, independent of status."""
    return make_proposal_version(
        proposal.ticker,
        proposal.trade_date,
        proposal.signal,
        proposal.price,
        side=proposal.side,
        shares=proposal.shares,
        evidence_id=proposal.evidence_id,
    )


def create_proposal(
    *,
    run_id: str,
    ticker: str,
    trade_date: str,
    signal: str,
    rating: str | None,
    price: float | None,
    proposal_id: str | None = None,
    evidence_id: str | None = None,
) -> ProposalRecord:
    """Create a PENDING_REVIEW proposal from a completed research run.

    Only tradeable signals become proposals: Buy-family signals are buys, Sell-
    family signals are sells (up to owned shares, enforced at execution). Hold
    and REVIEW never produce a tradeable recommendation.
    """
    if signal in ("Hold", "REVIEW"):
        raise ReviewError(
            f"signal {signal!r} is not tradeable in v1; no proposal is created "
            "(REVIEW and Hold do not trade)"
        )
    side = _side_for_signal(signal)
    pid = proposal_id or f"prop-{uuid.uuid4().hex[:12]}"
    return ProposalRecord(
        proposal_id=pid,
        run_id=run_id,
        ticker=ticker,
        trade_date=trade_date,
        signal=signal,
        rating=rating,
        side=side,
        price=price,
        evidence_id=evidence_id,
        status=ProposalStatus.PENDING_REVIEW,
        proposal_version=_proposal_content_version(
            ProposalRecord(
                proposal_id=pid,
                run_id=run_id,
                ticker=ticker,
                trade_date=trade_date,
                signal=signal,
                rating=rating,
                side=side,
                price=price,
                evidence_id=evidence_id,
            )
        ),
        created_at=utcnow_iso(),
    )


def approve(
    proposal: ProposalRecord,
    *,
    shares: int,
    operator: str,
) -> ProposalRecord:
    """Approve an exact proposal version with an operator-supplied share count.

    The approval is bound to the proposal's *content* version, so if the run's
    material inputs (ticker/date/signal/price) later change, the old approval
    no longer matches and execution requires review.
    """
    if proposal.status == ProposalStatus.SIMULATED:
        raise ReviewError(f"proposal {proposal.proposal_id} is already simulated")
    if proposal.status == ProposalStatus.REJECTED:
        raise ReviewError(f"proposal {proposal.proposal_id} is rejected and cannot be approved")
    # REVIEW_REQUIRED is a safe-fail state, not a dead end: after the operator
    # reviews the current evidence, they may approve the corrected version.
    if not operator:
        raise ReviewError("approval requires an operator identity")
    if not isinstance(shares, int) or shares <= 0:
        raise ReviewError(f"shares must be a positive integer, got {shares!r}")
    if proposal.price is None or proposal.price <= 0:
        raise ReviewError(
            f"proposal {proposal.proposal_id} has no evidence price; cannot approve without price"
        )
    proposal.shares = shares
    proposal.operator = operator
    proposal.status = ProposalStatus.APPROVED
    proposal.approved_at = utcnow_iso()
    proposal.approved_version = _proposal_content_version(proposal)
    return proposal


def reject(proposal: ProposalRecord, *, operator: str, reason: str = "rejected by operator") -> ProposalRecord:
    if proposal.status == ProposalStatus.SIMULATED:
        raise ReviewError(f"proposal {proposal.proposal_id} is already simulated")
    proposal.status = ProposalStatus.REJECTED
    proposal.operator = operator
    proposal.reason = reason
    return proposal


def execute(
    store, proposal: ProposalRecord, *, operator: str,
) -> tuple[ProposalRecord, ExecutionRecord]:
    """Re-evaluate the current ledger and simulate the approved buy (or reject).

    Steps (each observable, none partial):
    1. Idempotence: an already-SIMULATED proposal returns its stored execution.
    2. A REJECTED proposal is terminal: return unexecuted without changing its
       status or touching the store, so it can never be reopened for approval.
    3. Version binding: the current proposal content must match the approved
       version; otherwise REVIEW_REQUIRED (AT-05).
    4. Re-read the current ledger and run the deterministic policy.
    5. On any failure: return REVIEW_REQUIRED / BLOCKED with reasons; ledger
       unchanged. On success: apply the transaction atomically.
    """
    if proposal.status == ProposalStatus.SIMULATED:
        existing = proposal.execution or ExecutionRecord(executed=True)
        existing.reason = "already executed"
        return proposal, existing

    # A rejection is terminal. Check it before any version or generic status
    # transition so an execution attempt can never reopen it for approval.
    if proposal.status == ProposalStatus.REJECTED:
        return proposal, ExecutionRecord(executed=False, reason="proposal rejected")

    current_version = _proposal_content_version(proposal)
    # A stale approval for different content is checked before status: an
    # approved proposal whose run inputs changed must not execute the new
    # version (AT-05), even though the row now carries the new content.
    if proposal.approved_version is not None and proposal.approved_version != current_version:
        proposal.status = ProposalStatus.REVIEW_REQUIRED
        proposal.reason = (
            "approval no longer matches the proposal content (version changed "
            f"approved={proposal.approved_version!r} current={current_version!r}); "
            "re-review against the current ledger"
        )
        store.update_proposal_status(
            proposal.proposal_id,
            ProposalStatus.REVIEW_REQUIRED,
            operator=operator,
            reason=proposal.reason,
        )
        return proposal, ExecutionRecord(
            executed=False, reason=proposal.reason, policy_checks=[]
        )
    if proposal.status != ProposalStatus.APPROVED:
        proposal.status = ProposalStatus.REVIEW_REQUIRED
        proposal.reason = (
            f"proposal is not APPROVED (status={proposal.status.value}) and cannot "
            "execute; approve it against the current ledger first"
        )
        store.update_proposal_status(
            proposal.proposal_id,
            ProposalStatus.REVIEW_REQUIRED,
            operator=operator,
            reason=proposal.reason,
        )
        return proposal, ExecutionRecord(
            executed=False, reason=proposal.reason, policy_checks=[]
        )

    if proposal.shares is None or proposal.price is None:
        proposal.status = ProposalStatus.REVIEW_REQUIRED
        proposal.reason = "proposal missing shares or evidence price; cannot execute"
        store.update_proposal_status(
            proposal.proposal_id, ProposalStatus.REVIEW_REQUIRED, operator=operator,
            reason=proposal.reason,
        )
        return proposal, ExecutionRecord(executed=False, reason=proposal.reason, policy_checks=[])

    ledger = store.get_ledger()
    if ledger is None:
        raise ReviewError("ledger is not initialised")

    if proposal.side == "sell":
        return _execute_sell(store, proposal, ledger, operator=operator)
    verdict = evaluate_buy(ledger, proposal.ticker, proposal.shares, proposal.price)
    if not verdict.allowed:
        reasons = [f"{c['check']}: {c['detail']}" for c in verdict.checks if not c["passed"]]
        proposal.status = ProposalStatus.REVIEW_REQUIRED
        proposal.reason = "policy failed at execution time: " + "; ".join(reasons)
        store.update_proposal_status(
            proposal.proposal_id, ProposalStatus.REVIEW_REQUIRED, operator=operator,
            reason=proposal.reason,
        )
        return proposal, ExecutionRecord(
            executed=False,
            reason=proposal.reason,
            policy_checks=verdict.checks,
            equity_before=ledger.equity,
        )

    tx_id = f"tx-{uuid.uuid4().hex[:12]}"
    execution = ExecutionRecord(
        executed=True,
        tx_id=tx_id,
        policy_checks=verdict.checks,
        equity_before=ledger.equity,
        equity_after=ledger.equity,
        cash_delta=-proposal.shares * proposal.price,
    )
    tx = TransactionRecord(
        tx_id=tx_id,
        proposal_id=proposal.proposal_id,
        ticker=proposal.ticker,
        side="buy",
        shares=proposal.shares,
        price=proposal.price,
        cash_delta=execution.cash_delta,
        equity_before=ledger.equity,
        equity_after=ledger.equity,
        status=TransactionStatus.SIMULATED,
        policy_checks=verdict.checks,
        operator=operator,
        created_at=utcnow_iso(),
    )
    store.apply_transaction(tx, execution)
    proposal.status = ProposalStatus.SIMULATED
    proposal.execution = execution
    updated = store.get_proposal(proposal.proposal_id)
    return updated or proposal, proposal.execution


def _execute_sell(store, proposal: ProposalRecord, ledger, *, operator: str):

    shares = proposal.shares

        proposal.status = ProposalStatus.REVIEW_REQUIRED

    tx = TransactionRecord(

def evaluate_proposal_legibility(proposal: ProposalRecord) -> list[str]:

    issues: list[str] = []
    if proposal.status != ProposalStatus.APPROVED:
        issues.append(f"not APPROVED (status={proposal.status.value})")
    if proposal.shares is None or proposal.price is None:

    return issues


def now_iso() -> str:

FILE: src/research_desk/policy.py
"""Deterministic teaching-policy engine for the simulated ledger.

The deterministic policy constants are defined in ``research_desk.config``;
policy is never decided by an LLM. Every check returns a plain list of
human-readable results; the review layer turns a non-empty list of failures into
a business rejection and leaves the ledger untouched (INV-002). Boundary
behaviour is explicit: a position value exactly equal to 10% of equity is
allowed (<=), one share more is rejected.
"""

from __future__ import annotations

from dataclasses import dataclass

from .config import INITIAL_CASH, MAX_POSITION_PCT, NO_SHORTING
from .models import LedgerState


@dataclass
class PolicyVerdict:
    allowed: bool
    checks: list[dict]  # each: {"check": str, "passed": bool, "detail": str}
    equity: float | None = None
    position_value: float | None = None
    cash_after: float | None = None
    shares_after: int | None = None


def _owned_shares(ledger: LedgerState, ticker: str) -> int:
    pos = ledger.positions.get(ticker.upper())
    return pos.shares if pos is not None else 0


def _revalue_equity(ledger: LedgerState, ticker: str, mark_price: float) -> float:
    """Equity with the target ticker's holdings re-marked at the evidence price.

    The position cap is expressed as a fraction of equity, so the equity base
    must mark the ticker under review at the same (frozen evidence) price used
    for the trade. Other positions keep their recorded average mark, which is
    made explicit in the check detail rather than silently revalued.
    """
    ticker = ticker.upper()
    total = ledger.cash
    for t, pos in ledger.positions.items():
        if t == ticker and mark_price is not None and mark_price > 0:
            total += pos.shares * mark_price
        else:
            total += pos.shares * (pos.avg_price or 0.0)
    return total


class PolicyViolation(Exception):
    def __init__(self, reasons: list[str]):
        self.reasons = reasons
        super().__init__("; ".join(reasons))


def evaluate_buy(
    ledger: LedgerState,
    ticker: str,
    shares: int,
    price: float,
    *,
    initial_cash: float = INITIAL_CASH,
    max_position_pct: float = MAX_POSITION_PCT,
) -> PolicyVerdict:
    """Evaluate a buy proposal against the current ledger.

    Rules (v1 teaching policy):
    1. shares must be a positive integer.
    2. price must be positive and present (it always comes from evidence).
    3. cost (shares * price) must not exceed available cash.
    4. after the buy, the *total* position in this ticker (existing holdings at
       the evidence price plus the new shares) must be <= 10% of equity.
    5. no shorting (buys only increase a long position; never negative).

    ``initial_cash`` is recorded for the ledger seed; the effective cash check
    uses the current ledger's cash, which is ``initial_cash`` plus the sum of
    prior cash deltas. The position cap is against *total holdings after the
    purchase*, re-marking this ticker's existing shares at ``price``.
    """
    ticker = ticker.upper()
    checks: list[dict] = []

    def check(name: str, passed: bool, detail: str) -> None:
        checks.append({"check": name, "passed": passed, "detail": detail})

    if not isinstance(shares, int) or shares <= 0:
        check("integer_positive_shares", False, f"shares must be a positive integer, got {shares!r}")
        return PolicyVerdict(False, checks)

    if price is None or not isinstance(price, (int, float)) or price <= 0:
        check("price_from_evidence", False, f"price must be a positive number from evidence, got {price!r}")
        return PolicyVerdict(False, checks)

    equity = _revalue_equity(ledger, ticker, price)
    owned = _owned_shares(ledger, ticker)
    shares_after = owned + shares
    position_value = shares_after * price
    cash_after = ledger.cash - shares * price

    check("cash_sufficient", cash_after >= -1e-9, f"cost={shares * price:.2f}, cash={ledger.cash:.2f}")

    cap_value = max_position_pct * equity
    check(
        "position_cap_10pct",
        position_value <= cap_value + 1e-9,
        f"total holdings after buy ({owned} existing + {shares} new = {shares_after} sh "
        f"@ {price:.2f} = {position_value:.2f}) <= {max_position_pct:.0%} * equity={cap_value:.2f}",
    )

    check("no_shorting", NO_SHORTING, "v1 policy is buy-only; sell proposals use evaluate_sell")

    return PolicyVerdict(
        allowed=all(c["passed"] for c in checks),
        checks=checks,
        equity=equity,
        position_value=position_value,
        cash_after=cash_after,
        shares_after=shares_after,
    )


def evaluate_sell(
    ledger: LedgerState,
    ticker: str,
    shares: int,
    price: float,
    *,
    max_position_pct: float = MAX_POSITION_PCT,
) -> PolicyVerdict:
    """Evaluate a sell proposal against the current ledger.

    Sells are allowed only up to the shares actually owned (no shorting means
    a position can never go negative). The 10% concentration cap applies after a
    BUY; a valid SELL that reduces an owned position is permitted even if price
    appreciation means the remaining holding still exceeds 10% of equity.
    ``price`` comes from evidence; cash increases by ``shares * price``.
    """
    ticker = ticker.upper()
    checks: list[dict] = []

    def check(name: str, passed: bool, detail: str) -> None:
        checks.append({"check": name, "passed": passed, "detail": detail})

    if not isinstance(shares, int) or shares <= 0:
        check("integer_positive_shares", False, f"shares must be a positive integer, got {shares!r}")
        return PolicyVerdict(False, checks)

    if price is None or not isinstance(price, (int, float)) or price <= 0:
        check("price_from_evidence", False, f"price must be a positive number from evidence, got {price!r}")
        return PolicyVerdict(False, checks)

    owned = _owned_shares(ledger, ticker)
    equity = _revalue_equity(ledger, ticker, price)
    shares_after = owned - shares
    position_value = shares_after * price
    cash_after = ledger.cash + shares * price

    check(
        "sell_not_exceeding_owned",
        shares_after >= 0,
        f"cannot sell {shares} sh when {owned} sh are owned (no shorting); "
        f"sell at most {owned} sh",
    )

    return PolicyVerdict(
        allowed=all(c["passed"] for c in checks),
        checks=checks,
        equity=equity,
        position_value=position_value,
        cash_after=cash_after,
        shares_after=shares_after,
    )


def raise_for_violations(verdict: PolicyVerdict) -> None:
    """Raise a PolicyViolation listing every failed check (no partial writes)."""
    if not verdict.allowed:
        reasons = [f"{c['check']}: {c['detail']}" for c in verdict.checks if not c["passed"]]
        raise PolicyViolation(reasons)


def reject_reasons(verdict: PolicyVerdict) -> list[str]:
    return [f"{c['check']}: {c['detail']}" for c in verdict.checks if not c["passed"]]


def policy_bounds(
    ledger: LedgerState,
    ticker: str,
    price: float | None,
    *,
    max_position_pct: float = MAX_POSITION_PCT,
) -> dict:
    """Deterministic policy limits for a proposal price against a ledger.

    Reported by offline replay so the *policy output* (the largest integer
    share count the teaching policy would allow) is reproduced without needing
    the operator's eventual share choice. ``max_by_cap`` is the additional
    shares a *buy* may add given existing holdings must stay within the total
    position cap.
    """
    if price is None or price <= 0:
        return {
            "price_present": False,
            "max_by_cap": None,
            "max_by_cash": None,
            "owned": _owned_shares(ledger, ticker),
            "equity": ledger.equity,
            "cash": ledger.cash,
        }
    cap_value = max_position_pct * _revalue_equity(ledger, ticker, price)
    owned = _owned_shares(ledger, ticker)
    max_total = int(cap_value // price)
    return {
        "price_present": True,
        "max_by_cap": max_total - owned,  # additional shares still within total cap
        "max_by_cash": int(ledger.cash // price),
        "owned": owned,
        "equity": _revalue_equity(ledger, ticker, price),
        "cash": ledger.cash,
    }

"""LLM call budget and usage accounting for a research run.

The budget counts *started* LLM calls and the actual token usage reported by
the provider. Enforcement happens in the evidence recorder's
``on_chat_model_start``: once the configured call limit is reached, the next
call raises :class:`BudgetExhausted` so the graph aborts and no further LLM
request is started (NFR-003). A budget-stopped run returns incomplete research
and is never turned into an approvable recommendation.

This module also owns the whole-input context bound (ADR-004): a conservative
UTF-8 byte-based token upper bound estimates the complete request; when the
mandatory material still exceeds the cap the caller raises
:class:`ContextBudgetExceeded` before the provider is invoked.
"""

from __future__ import annotations

import json
import threading
from collections.abc import Sequence
from dataclasses import dataclass, field
from typing import Any

from langchain_core.messages import BaseMessage

from .models import CallUsage, UsageSummary

# Conservative fixed per-message/per-tool-call overhead added to the UTF-8 byte
# count. This keeps the estimate an *upper bound* on provider tokens; it is not
# measured token usage (provider usage remains the measured-cost source).
CONTEXT_MESSAGE_OVERHEAD = 8
CONTEXT_TOOL_CALL_OVERHEAD = 16


class BudgetExhausted(Exception):
    """Raised when the configured LLM call budget is exhausted."""

    def __init__(self, limit: int):
        self.limit = limit
        super().__init__(f"LLM call budget exhausted (limit={limit}); refusing to start next call")


class ContextBudgetExceeded(Exception):
    """Raised when the complete model input cannot fit under the context cap.

    Raised at the request boundary *before* the provider is invoked, so the run
    stops with an incomplete, non-approvable outcome while evidence remains
    inspectable.
    """

    stop_reason = "context_budget_exhausted"

    def __init__(self, estimated_tokens: int, limit: int):
        self.estimated_tokens = estimated_tokens
        self.limit = limit
        super().__init__(
            f"context budget exhausted (estimated={estimated_tokens} > limit={limit}); "
            "refusing to start LLM call"
        )


def _content_units(content: Any) -> int:
    """Conservative UTF-8 byte count for a message content value."""
    if content is None:
        return 0
    if isinstance(content, str):
        return len(content.encode("utf-8"))
    if isinstance(content, (list, tuple)):
        total = 0
        for part in content:
            if isinstance(part, str):
                total += len(part.encode("utf-8"))
            elif isinstance(part, dict):
                total += len(
                    json.dumps(part, ensure_ascii=False, default=str).encode("utf-8")
                )
            else:
                total += len(str(part).encode("utf-8"))
        return total
    return len(str(content).encode("utf-8"))


def estimate_input_units(messages: Sequence[BaseMessage]) -> int:
    """Conservative token upper bound for a complete message list.

    Counts every message's role/type, content, name, tool-call structure and
    ``tool_call_id`` as UTF-8 bytes plus fixed overhead. This deliberately does
    not call a provider tokenizer and must not be reported as measured usage.
    """
    total = 0
    for msg in messages:
        total += CONTEXT_MESSAGE_OVERHEAD
        total += len(str(getattr(msg, "type", "")).encode("utf-8"))
        total += _content_units(getattr(msg, "content", None))
        name = getattr(msg, "name", None)
        if name:
            total += len(str(name).encode("utf-8"))
        tool_call_id = getattr(msg, "tool_call_id", None)
        if tool_call_id:
            total += len(str(tool_call_id).encode("utf-8"))
        tool_calls = getattr(msg, "tool_calls", None)
        if tool_calls:
            total += CONTEXT_TOOL_CALL_OVERHEAD * len(tool_calls)
            total += len(
                json.dumps(tool_calls, ensure_ascii=False, default=str).encode("utf-8")
            )
    return total


@dataclass
class BudgetTracker:
    """Thread-safe per-run call budget + usage accumulator.

    ``stop_reason`` distinguishes an *actually blocked* next call (a request was
    refused with :class:`BudgetExhausted`) from a normal completion that simply
    used at most ``max_calls`` calls. A run that reaches the limit on its final
    allowed call without ever requesting another is ``completed``; only a run
    whose next call was refused is ``budget_exhausted``.
    """

    max_calls: int | None = None
    _lock: threading.Lock = field(default_factory=threading.Lock, repr=False)
    calls_started: int = 0
    blocked: bool = False  # a call was actually refused (BudgetExhausted raised)
    usage: UsageSummary = field(default_factory=UsageSummary)

    def can_start(self) -> bool:
        """Whether a new LLM call is permitted under the budget."""
        if self.max_calls is None:
            return True
        return self.calls_started < self.max_calls

    def start_call(self) -> None:
        """Register the start of an LLM call; raise when budget exhausted."""
        with self._lock:
            limit = self.max_calls
            if limit is not None and self.calls_started >= limit:
                self.blocked = True
                raise BudgetExhausted(limit)
            self.calls_started += 1

    def record_usage(self, usage: CallUsage) -> None:
        with self._lock:
            self.usage.add(usage)

    def stop_reason(self) -> str:
        if self.blocked:
            return "budget_exhausted"
        return "completed"

    def summary(self) -> UsageSummary:
        with self._lock:
            return UsageSummary(
                calls=self.calls_started,
                input_tokens=self.usage.input_tokens,
                output_tokens=self.usage.output_tokens,
                total_tokens=self.usage.total_tokens,
                stop_reason=self.stop_reason(),
            )

    def merge(self, other: BudgetTracker) -> None:
        """Merge another tracker's counts (used to aggregate baseline/compact arms)."""
        with self._lock:
            self.calls_started += other.calls_started
            self.blocked = self.blocked or other.blocked
            self.usage.calls += other.usage.calls
            self.usage.input_tokens += other.usage.input_tokens
            self.usage.output_tokens += other.usage.output_tokens
            self.usage.total_tokens += other.usage.total_tokens

"""Source-bound release evidence validation (ADR-004).

Provenance lives at <evidence>/<TICKER>/<mode>/provenance.json and
<evidence>/judge/<TICKER>/<mode>/provenance.json as

import hashlib
import json
from pathlib import Path
from typing import Any, TypeGuard

from ..config import DEFAULT_MODEL, DEFAULT_PROVIDER

MODES = ("baseline", "compact")
PROVENANCE = "provenance.json"
MANDATORY = ("instrument_identity", "analysis_date", "final_decision_present", "frozen_price_in_report", "source_id_referenced")
SETTINGS = ("llm_provider", "quick_think_llm", "deep_think_llm", "max_tokens", "temperature", "llm_max_retries", "max_debate_rounds", "max_risk_discuss_rounds", "extra_body", "backend_url", "checkpoint_enabled")

def _source_paths(root: Path) -> list[Path]:
    root = Path(root)
    python_sources = [p for p in root.glob("src/research_desk/**/*.py") if p.is_file()]
    prompts = [
        p
        for pattern in ("prompts/**/*.yaml", "prompts/**/*.yml")
        for p in root.glob(pattern)
        if p.is_file()
    ]
    groups = [python_sources, prompts]
    required = [root / r for r in ("pyproject.toml", "requirements-lock.txt", "test/fixtures/market/orchestration-manifest.json")]
    market = [p for p in (root / "test/fixtures/market").glob("*.csv") if p.is_file()]
    if any(not g for g in groups + [market]) or not all(p.is_file() for p in required):
        raise FileNotFoundError(f"required runtime source files missing under {root}")
    return sorted([p for g in groups + [market] for p in g] + required, key=lambda p: p.relative_to(root).as_posix())


def source_fingerprint(root: Path) -> str:
    """SHA-256 of sorted relative runtime filenames plus contents."""
    root = Path(root).resolve()
    digest = hashlib.sha256()
    for path in _source_paths(root):
        digest.update(path.relative_to(root).as_posix().encode("utf-8"))
        digest.update(b"\0")
        digest.update(hashlib.sha256(path.read_bytes()).digest())
    return "sha256:" + digest.hexdigest()


def _json(path: Path, label: str, failures: list[str]) -> Any:
    try:
        return json.loads(Path(path).read_text(encoding="utf-8"))
    except Exception as exc:  # noqa: BLE001
        failures.append(f"{label}: cannot read {Path(path).name}: {exc}")
        return None


def _num(value: Any) -> TypeGuard[int | float]:
    return isinstance(value, (int, float)) and not isinstance(value, bool)


def _provenance(rec: Any, current: str | None, label: str, kind: str, failures: list[str]) -> None:
    if not isinstance(rec, dict):
        failures.append(f"{label}: {kind} provenance is not an object")
        return
    if current is None or rec.get("source_fingerprint") != current:
        failures.append(f"{label}: {kind} provenance has a stale or incorrect source fingerprint")
    for key, expected in (("model", DEFAULT_MODEL), ("provider", DEFAULT_PROVIDER)):
        if rec.get(key) != expected:
            failures.append(f"{label}: {kind} provenance {key} {rec.get(key)!r} != {expected!r}")


def _summary(summary: dict[str, Any], ticker: str, mode: str, label: str, failures: list[str]) -> None:
    for key, expected in (("ticker", ticker), ("context_mode", mode), ("outcome", "completed"), ("pack_complete", True)):
        got = summary.get(key)
        if (str(got).upper() if key == "ticker" else got) != expected:
            failures.append(f"{label}: summary {key} mismatch")
    if summary.get("error") not in (None, "", False):
        failures.append(f"{label}: summary records an error")
    calls = summary.get("calls")
    input_tokens = summary.get("input_tokens")
    output_tokens = summary.get("output_tokens")
    total_tokens = summary.get("total_tokens")
    if (
        not _num(calls)
        or not _num(input_tokens)
        or not _num(output_tokens)
        or not _num(total_tokens)
        or calls <= 0
        or input_tokens <= 0
        or output_tokens <= 0
        or total_tokens <= 0
        or total_tokens != input_tokens + output_tokens
    ):
        failures.append(f"{label}: usage is not positive or total_tokens != input + output")
    if not _num(summary.get("wall_seconds")) or summary["wall_seconds"] < 0:
        failures.append(f"{label}: wall_seconds is missing or negative")


def _pack(pack: Any, summary: dict[str, Any], ticker: str, mode: str, case: dict, label: str, failures: list[str]) -> dict[str, dict[str, Any]]:
    if not pack.complete or pack.manifest.outcome != "completed":
        failures.append(f"{label}: saved actual pack is incomplete or not completed")
    if str(pack.manifest.ticker).upper() != ticker or pack.manifest.context_mode != mode:
        failures.append(f"{label}: saved actual pack identity/mode mismatch")
    usage = pack.usage
    values = {k: getattr(usage, k) for k in ("calls", "input_tokens", "output_tokens", "total_tokens")}
    if any(not _num(v) or v <= 0 for v in values.values()) or usage.total_tokens != usage.input_tokens + usage.output_tokens:
        failures.append(f"{label}: saved pack usage is not positive or total_tokens != input + output")
    for key, value in values.items():
        if summary.get(key) != value:
            failures.append(f"{label}: summary {key} does not match the saved actual pack")
    try:
        from .live import _deterministic_checks
        return {c["check"]: c for c in _deterministic_checks(case, pack, ticker) if isinstance(c, dict) and isinstance(c.get("check"), str)}
    except Exception as exc:  # noqa: BLE001
        failures.append(f"{label}: cannot recompute checks from saved actual pack: {exc}")
        return {}


def _judge(judge: dict[str, Any], recomputed: dict[str, dict[str, Any]], label: str, failures: list[str]) -> None:
    for key, expected, message in (("error", False, "judge error is not false"), ("semantic_valid", True, "semantic_valid is not true")):
        if judge.get(key) is not expected:
            failures.append(f"{label}: {message}")
    for key, minimum in (("support", MIN_SUPPORT), ("relevance", MIN_RELEVANCE), ("valid_citation_rate", MIN_CITATION)):
        if not _num(judge.get(key)) or judge[key] < minimum:
            failures.append(f"{label}: {key} below {minimum}")
    if judge.get("semantic_errors") != []:
        failures.append(f"{label}: semantic_errors is not empty")
    saved = {c["check"]: c for c in (judge.get("deterministic_checks") or []) if isinstance(c, dict) and isinstance(c.get("check"), str)}
    for name in MANDATORY:
        saved_check = saved.get(name)
        if saved_check is None:
            failures.append(f"{label}: mandatory deterministic check missing: {name}")
        elif saved_check.get("passed") is not True:
            failures.append(f"{label}: deterministic check failed: {name}")
        if recomputed and (recomputed.get(name) is None or recomputed[name].get("passed") is not True):
            failures.append(f"{label}: recomputed pack check failed: {name}")
        elif recomputed and saved_check is not None and saved_check.get("passed") != recomputed[name].get("passed"):
            failures.append(f"{label}: saved check disagrees with saved actual pack: {name}")


def validate_release(root: Path, evidence_dir: Path) -> dict[str, Any]:

    for ticker in sorted(expected - present):

    for ticker in sorted(present - expected):
        failures.append(f"unexpected case identity: {ticker}")
    checks.append(f"RELEASE_CASES={len(expected)}")

            failures.append(f"{ticker}: settings differ across arms")
        if (baseline["jprov"].get("model"), baseline["jprov"].get("provider")) != (compact["jprov"].get("model"), compact["jprov"].get("provider")):

        ratio = cw / bw if bw > 0 else None
        mean_support_baseline = sum(m["baseline_support"] for m in paired) / len(paired)
        mean_support_compact = sum(m["compact_support"] for m in paired) / len(paired)
        support_drop = mean_support_baseline - mean_support_compact
        mean_relevance_baseline = sum(m["baseline_relevance"] for m in paired) / len(paired)
        mean_relevance_compact = sum(m["compact_relevance"] for m in paired) / len(paired)
        relevance_drop = mean_relevance_baseline - mean_relevance_compact
        metrics["aggregate"] = {
            "token_reduction": reduction,
            "mean_support_baseline": mean_support_baseline,
            "mean_support_compact": mean_support_compact,
            "mean_support_drop": support_drop,
            "mean_relevance_baseline": mean_relevance_baseline,
            "mean_relevance_compact": mean_relevance_compact,
            "mean_relevance_drop": relevance_drop,
            "wall_ratio": ratio,
        }
        metrics["should_targets"] = {
            "token_reduction": {
                "value": reduction,
                "target": f">={COST_MIN}",
                "passed": reduction is not None and reduction >= COST_MIN,
            },
            "mean_support_drop": {
                "value": support_drop,
                "target": f"<={QUALITY_DROP_MAX}",
                "passed": support_drop <= QUALITY_DROP_MAX,
            },
            "mean_relevance_drop": {
                "value": relevance_drop,
                "target": f"<={QUALITY_DROP_MAX}",
                "passed": relevance_drop <= QUALITY_DROP_MAX,
            },
            "wall_ratio": {
                "value": ratio,
                "target": f"<={WALL_MAX}",
                "passed": ratio is not None and ratio <= WALL_MAX,
            },
        }
        for name, target in metrics["should_targets"].items():
            status = "PASS" if target["passed"] else "FAIL"
            checks.append(
                f"RELEASE_SHOULD {name}={target['value']} target {target['target']} {status}"
            )
            if not target["passed"] and name not in ("mean_support_drop", "mean_relevance_drop"):
                warnings.append(
                    f"Should target missed: {name}={target['value']} target {target['target']}"
                )
        if support_drop > QUALITY_DROP_MAX:
            failures.append(
                f"quality retention failed: mean support drop {support_drop:.4f} > {QUALITY_DROP_MAX}"
            )
        if relevance_drop > QUALITY_DROP_MAX:
            failures.append(
                f"quality retention failed: mean relevance drop {relevance_drop:.4f} > {QUALITY_DROP_MAX}"
            )
    return {"failures": failures, "checks": checks, "warnings": warnings, "metrics": metrics, "source_fingerprint": current}

"""Per-agent COMMON grounding + prompt compaction on the real LLM inputs.

Fresh evaluation runs have essentially no past memory, so compressing only
``past_context`` has almost no effect, and that header is not even read by many
downstream upstream roles. This module fixes the shared grounding/citation
failure by wrapping the real LangChain chat model with a small plain delegate
(exposing ``invoke``, ``bind_tools`` and ``with_structured_output``) that
injects the identical COMMON grounding layer into *every* request in BOTH modes
(baseline and compact), while retaining the real LangChain client and the
upstream ``GraphSetup``.

- The common grounding layer carries the real per-case ticker, legal company
  identity, analysis date, frozen close, the source-ID registry
  (``src-<ticker>`` = official earnings news, ``market-<ticker>`` = market
  CSV/technical computations), the short official earnings notes and citation
  rules. It is the shared correctness fix applied to both arms.
- For ``context_mode == "baseline"`` the delegate only prepends the common
  grounding layer; the substantive prompt/history is left uncompressed (no
  artificial padding, no rewrite).
- For ``compact`` the delegate additionally trims redundant message text,
  de-duplicates, and appends a concise-output instruction, while preserving key
  quoted facts (the standing-constraints and source markers) in every prompt.

Message integrity rules (review finding #1):

- A message is rebuilt with the declared model-copy/update API, changing only
  ``content``. ``AIMessage.tool_calls``, ``ToolMessage.tool_call_id``,
  ``id``/``name`` and every other field are preserved — never re-created.
- A ``ToolMessage`` that answers an assistant tool call is never de-duplicated
  away and never truncated: dropping or merging it would break the assistant's
  pending tool call.
- An ``AIMessage`` that carries ``tool_calls`` (typically with empty ``content``)
  is kept, never dropped, even though its text is empty.
- Evidence messages (messages carrying a ``_FACT_MARKERS`` token) are not
  truncated. Trimming only verbose, non-fact prose is allowed; discarding
  numbers, identity, dates or sources is not.
- The concise-output instruction targets ~600 tokens for compact roles while
  the provider ``max_tokens`` stays 1800 in both arms (set in the graph config).
"""

# Content markers that carry the facts which must survive compaction. A message

    "last_close",
    "NO_DATA_AVAILABLE",
    "source_id",
    "src-",
    "USD",

    "Instrument identity",
    "trade_date",
    "past_context",

    "Do not repeat the input; only output the requested analysis."

def _tuple_to_message(role: str, content: Any) -> BaseMessage | None:
    """Map a ``(role, content)`` pair to a message, or None for an unknown role."""
    role = (role or "").lower()
    if role == "system":
        return SystemMessage(content=content)
    if role in ("human", "user"):
        return HumanMessage(content=content)
    if role in ("ai", "assistant"):
        return AIMessage(content=content)
    return None


def _to_messages(input: Any) -> list[BaseMessage] | None:
    """Normalise a model input to a list of messages, or None if not list-like."""
    if isinstance(input, list) and all(isinstance(m, BaseMessage) for m in input):
        return list(input)
    if isinstance(input, str):
        return [HumanMessage(content=input)]
    if isinstance(input, (list, tuple)) and input and all(
        isinstance(p, (list, tuple)) and len(p) == 2 for p in input
    ):
        mapped = [_tuple_to_message(role, content) for role, content in input]
        if all(m is not None for m in mapped):
            return [m for m in mapped if m is not None]
        return None  # unknown role: pass through unchanged rather than drop content
    if hasattr(input, "to_messages"):
        try:
            return input.to_messages()
        except Exception:  # noqa: BLE001 - PromptValue edge cases
            return None
    return None


def _content_of(msg: BaseMessage) -> str:
    c = msg.content
    return c if isinstance(c, str) else str(c)


def _has_fact_marker(text: str) -> bool:
    low = text.lower()
    return any(marker.lower() in low for marker in _FACT_MARKERS)


def _rebuild(msg: BaseMessage, content: str) -> BaseMessage:
    """Rebuild a message with only ``content`` changed; preserve every other field.

    ``model_copy(update=...)`` keeps ``type``, ``id``, ``name``, ``tool_calls``,
    ``tool_call_id``, ``additional_kwargs`` and any subclass state intact, so an
    ``AIMessage`` keeps its tool calls and a ``ToolMessage`` keeps the
    ``tool_call_id`` the assistant is waiting on.
    """
    return msg.model_copy(update={"content": content})


def compact_transform(
    input: Any,
    *,
    max_output_tokens: int = 600,
    max_msg_chars: int = 1500,
    fact_floor_chars: int = 6000,
) -> Any:
    """Transform a per-agent prompt for the compact arm.

    Keeps message roles, trims verbose non-fact prose to ``max_msg_chars``,
    removes exact duplicate messages (never a tool response), and appends a
    concise-output instruction. Messages carrying key facts are preserved so no
    grounding marker is dropped. Every message is rebuilt via
    :func:`_rebuild`, so tool-call state survives unchanged.
    """
    messages = _to_messages(input)
    if messages is None:
        return input  # cannot transform; pass through unchanged

    seen: set[str] = set()
    kept: list[BaseMessage] = []
    for msg in messages:
        content = _content_of(msg)
        if isinstance(msg, ToolMessage):
            # A tool response answers an assistant tool call: never dedupe,
            # never truncate, never drop — the assistant is waiting on it.
            kept.append(msg)
            continue
        if isinstance(msg, AIMessage) and getattr(msg, "tool_calls", None):
            # An assistant message that issued tool calls (text may be empty);
            # keep it whole so the tool_calls survive to the next turn.
            kept.append(_rebuild(msg, content))
            continue
        if not content:
            continue
        if content in seen:
            continue  # drop exact duplicate prose messages only
        seen.add(content)
        if not _has_fact_marker(content) and len(content) > max_msg_chars:
            content = content[:max_msg_chars].rstrip() + "\n[... compacted ...]"
        kept.append(_rebuild(msg, content))

    kept.append(
        SystemMessage(content=_OUTPUT_INSTRUCTION.format(max_tokens=max_output_tokens))
    )
    return kept


_COMPACTED_MARKER = "\n[... context compacted ...]"
_BUDGET_PROSE_CHARS = 240


def _is_expendable_old_prose(
    msg: BaseMessage, index: int, latest_human: int
) -> bool:
    """Whether an old, non-fact plain prose message may be compacted/removed.

    System constraints, the latest user/task, fact-bearing evidence and every
    assistant/tool-call group member are never expendable.
    """
    if index == latest_human:
        return False
    if not isinstance(msg, (HumanMessage, AIMessage)):
        return False
    if isinstance(msg, AIMessage) and getattr(msg, "tool_calls", None):
        return False
    return not _has_fact_marker(_content_of(msg))


def enforce_context_budget(
    messages: list[BaseMessage],
    *,
    trigger_tokens: int,
    max_tokens: int,
    prose_chars: int = _BUDGET_PROSE_CHARS,
) -> tuple[list[BaseMessage], bool, int]:
    """Bound a complete message list, preserving mandatory material.

    Below ``trigger_tokens`` the input is returned unchanged. Above it, older
    expendable non-fact prose is first shortened and then dropped oldest-first.
    System constraints, the latest user/task, fact-bearing evidence and entire
    assistant tool-call / ToolMessage groups are never removed. If the required
    material still exceeds ``max_tokens``, raise :class:`ContextBudgetExceeded`
    before the provider is invoked.

    Returns ``(messages, compacted, before_units)``.
    """
    before = estimate_input_units(messages)
    if before <= trigger_tokens and before <= max_tokens:
        return list(messages), False, before

    latest_human = max(
        (i for i, m in enumerate(messages) if isinstance(m, HumanMessage)),
        default=-1,
    )
    expendable = [
        i
        for i, m in enumerate(messages)
        if _is_expendable_old_prose(m, i, latest_human)
    ]

    compacted_messages: list[BaseMessage] = []
    for i, msg in enumerate(messages):
        if i in expendable:
            content = _content_of(msg)
            if len(content) > prose_chars:
                content = content[:prose_chars].rstrip() + _COMPACTED_MARKER
            compacted_messages.append(_rebuild(msg, content))
        else:
            compacted_messages.append(msg)

    after = estimate_input_units(compacted_messages)
    if after > max_tokens:
        dropped: set[int] = set()
        for i in expendable:
            dropped.add(i)
            candidate = [m for j, m in enumerate(compacted_messages) if j not in dropped]
            after = estimate_input_units(candidate)
            if after <= max_tokens:
                compacted_messages = candidate
                break
        else:
            compacted_messages = [
                m for j, m in enumerate(compacted_messages) if j not in dropped
            ]
            after = estimate_input_units(compacted_messages)

    if after > max_tokens:
        raise ContextBudgetExceeded(after, max_tokens)
    return compacted_messages, True, before


def delegate_transform(
    input: Any,
    *,
    context_mode: str,
    common_grounding: str,
    max_output_tokens: int = 600,
    max_msg_chars: int = 1500,
) -> Any:
    """Inject the COMMON grounding layer into a request, then compact if needed.

    Both modes prepend the identical ``common_grounding`` SystemMessage so every
    request (analyst, researcher, trader, risk, portfolio manager, reflection)
    sees the same source registry, facts and citation rules.

    - baseline: substantive history is left untouched (grounding is the only
      addition, the shared correctness fix).
    - compact: the original substantive messages are then de-duplicated/trimmed
      and a concise-output instruction appended (unchanged 600-token target;
      provider ``max_tokens`` cap stays 1800 in both arms).

    Un-transformable inputs (None / unknown shapes) pass through unchanged.
    """
    messages = _to_messages(input)
    if messages is None:
        return input
    if context_mode == "compact":
        body = compact_transform(
            messages,
            max_output_tokens=max_output_tokens,
            max_msg_chars=max_msg_chars,
        )
    else:
        body = list(messages)
    return [SystemMessage(content=common_grounding)] + list(body)


class GroundingDelegate:
    """A small plain delegate around the real LangChain client.

    ``invoke`` transforms and delegates; ``bind_tools`` and
    ``with_structured_output`` delegate to the *real* client's binding and then
    compose a ``RunnableLambda`` preprocessor with the returned Runnable, so the
    common grounding layer reaches every invocation through every path. There is
    no dynamic ``__class__`` mutation and no dropped tool responses: the real
    client's returned ``AIMessage.tool_calls`` and ``ToolMessage.tool_call_id``
    are preserved exactly because the composed runnables hand them through
    untouched.
    """

    def __init__(
        self,
        llm: Any,
        *,
        context_mode: str,
        common_grounding: str,
        max_output_tokens: int = 600,
        max_msg_chars: int = 1500,
        context_max_tokens: int = DEFAULT_CONTEXT_MAX_TOKENS,
        context_trigger_tokens: int = DEFAULT_CONTEXT_TRIGGER_TOKENS,
        budget_observer: BudgetObserver | None = None,
    ):
        from langchain_core.runnables import RunnableLambda

        self.llm = llm
        self.context_mode = context_mode
        self.common_grounding = common_grounding
        self.max_output_tokens = max_output_tokens
        self.max_msg_chars = max_msg_chars
        self.context_max_tokens = context_max_tokens
        self.context_trigger_tokens = context_trigger_tokens
        self.budget_observer = budget_observer
        self._pre = RunnableLambda(self._transform)

    def _transform(self, input: Any) -> Any:
        transformed = delegate_transform(
            input,
            context_mode=self.context_mode,
            common_grounding=self.common_grounding,
            max_output_tokens=self.max_output_tokens,
            max_msg_chars=self.max_msg_chars,
        )
        complete = _to_messages(transformed)
        if complete is None:
            return transformed

        bounded, compacted, before = enforce_context_budget(
            complete,
            trigger_tokens=self.context_trigger_tokens,
            max_tokens=self.context_max_tokens,
        )
        after = estimate_input_units(bounded)
        logger.info(
            "context budget conservative_units before=%d after=%d trigger=%d cap=%d "
            "compacted=%s mode=%s",
            before,
            after,
            self.context_trigger_tokens,
            self.context_max_tokens,
            compacted,
            self.context_mode,
        )
        if self.budget_observer is not None:
            self.budget_observer(
                {
                    "before_units": before,
                    "after_units": after,
                    "trigger": self.context_trigger_tokens,
                    "cap": self.context_max_tokens,
                    "compacted": compacted,
                    "metric": "utf8_upper_bound",
                }
            )
        return bounded

    def invoke(self, input: Any, config: Any = None, **kwargs: Any) -> Any:
        return self.llm.invoke(self._pre.invoke(input, config), config, **kwargs)

    def bind_tools(self, tools: Any, **kwargs: Any) -> Any:
        bound = self.llm.bind_tools(tools, **kwargs)
        return self._pre | bound

    def with_structured_output(self, schema: Any, **kwargs: Any) -> Any:
        structured = self.llm.with_structured_output(schema, **kwargs)
        return self._pre | structured


def wrap_for_mode(
    llm: Any,
    context_mode: str,
    *,
    common_grounding: str,
    max_output_tokens: int = 600,
    max_msg_chars: int = 1500,
    context_max_tokens: int = DEFAULT_CONTEXT_MAX_TOKENS,
    context_trigger_tokens: int = DEFAULT_CONTEXT_TRIGGER_TOKENS,
    budget_observer: BudgetObserver | None = None,
) -> Any:
    """Wrap ``llm`` with a :class:`GroundingDelegate` for BOTH modes.

    The delegate injects the identical COMMON grounding layer into every
    request; baseline leaves the substantive history untouched while compact
    also trims/de-duplicates and appends the concise-output instruction. Every
    request is then bounded by the whole-input context budget, and an optional
    observer receives the conservative before/after units.
    """
    return GroundingDelegate(
        llm,
        context_mode=context_mode,
        common_grounding=common_grounding,
        max_output_tokens=max_output_tokens,
        max_msg_chars=max_msg_chars,
        context_max_tokens=context_max_tokens,
        context_trigger_tokens=context_trigger_tokens,
        budget_observer=budget_observer,
    )

class _RecordingModel:
    def __init__(self) -> None:
        self.calls: list = []

    def invoke(self, input, config=None, **kwargs):
        self.calls.append(input)
        return AIMessage(content="ok")

    def bind_tools(self, tools, **kwargs):
        return _RecordingBound(self)

    def with_structured_output(self, schema, **kwargs):
        return _RecordingStructured(self)


class _RecordingBound:
    def __init__(self, model: _RecordingModel) -> None:
        self.model = model

    def __call__(self, input):
        self.model.calls.append(input)
        return AIMessage(
            content="",
            tool_calls=[
                {"name": "get_stock_data", "args": {}, "id": "call_1", "type": "tool_call"}
            ],
        )


class _RecordingStructured:
    def __init__(self, model: _RecordingModel) -> None:
        self.model = model

    def __call__(self, input):
        self.model.calls.append(input)
        return {"ok": True}


def _delegate(model, *, mode="baseline", cap=2000, trigger=1000) -> GroundingDelegate:

This project uses a genuine language-model research graph to investigate a practical software engineering question: how can a user inspect the evidence behind an AI recommendation, reproduce its presentation, and control the consequences of accepting it? The delivered workflow connects research to a portable evidence package, then to an explicitly approved paper transaction. A second workflow compares the cost and quality of two context strategies using the same underlying research system.

## 1. Problem, scope and contribution

TradingAgents is a substantial existing multi-agent application. It already separates research perspectives, produces structured decisions and retains research memory. Its reports are valuable to a reader, but an engineering assessment needs additional evidence about how a particular report was produced and what an application may do with it. A saved report alone does not identify every material input or establish that a later action followed the user's approval.

Research Desk delivers five requirement increments through three integrated workflows. Portable evidence and approved paper transactions are the first two increments. Context optimization is the third. The revision adds a complete-input budget and source-bound release acceptance. The table in docs/process/team.md maps these five increments to requirements and evidence. The first captures a run as a transferable evidence package and reconstructs the report in a new process without external calls. The second turns a completed recommendation into an operator-reviewed proposal and applies a paper transaction only after deterministic checks. The third adds context and request-budget controls, then measures a baseline/compact comparison over six fixed cases. Each feature participates in an end-to-end user workflow rather than existing as an isolated demonstration.

The evidence workflow answers the operator's question, “What did this run actually see?” Its package records instrument identity, analysis cutoff, material tool inputs, model requests, model responses and terminal state. Actual provider usage accompanies the calls. The package can be exported as a ZIP and inspected on another machine. The replay path reconstructs saved results, so it has no reason to instantiate a model client. A controlled rerun has a different purpose: it executes the research graph again against the same frozen data, allowing an experiment on context strategy.

The transaction workflow answers, “Which action did I approve?” A proposal includes the research evidence reference, direction, price and operator-selected quantity. Approval refers to exact terms. If those terms change, the old approval cannot authorize the new proposal. The policy checks the current ledger at execution time because the user's earlier review cannot freeze cash or holdings indefinitely. Repeating an already completed execution returns the original transaction instead of applying a second financial side effect.

The context workflow asks whether repeated prompt material can be reduced without damaging evidence-grounded research. The complete selected upstream graph remains in place for both arms. The same DeepSeek model and inference settings are used. The source corpus is fixed before the comparison. Actual token usage supplies the cost measure, while an independent assessment supplies the quality measure. The request budget also provides a concrete degraded-mode behavior: a stopped research run remains inspectable but does not create an approvable recommendation.

The scope deliberately fits a single local operator. The application handles US equities with the market and news analysts, retains the downstream researcher/trader/risk roles, and produces English reports. It offers CLI commands and readable report artifacts. It operates strictly on a local paper ledger without broker integration or live order routing, keeping the execution safety boundary deterministic and testable.

## 3. Requirements engineering and acceptance strategy

The machine-readable product requirements document identifies the user and the integrated application workflows. A consolidated registry contains 24 requirements. Each entry has an identifier, type, statement, priority and a fit criterion expressed as a metric, comparison operator, threshold and verification method. Source links identify inherited behavior. Component and test references make the registry useful to implementation and CI rather than merely readable prose.

The priorities follow MoSCoW. Correct evidence handling, deterministic authority and complete measurement are Must requirements. A 20% token reduction and a compact wall time within 110% of baseline are Should targets. This prioritization decouples deterministic safety enforcement from empirical optimization targets during acceptance evaluation.

The strongest invariants have zero-tolerance fit criteria. Every ledger mutation must refer to exact approved terms and passing current-state policy checks. An unapproved, rejected, nontradeable or policy-violating proposal must leave the ledger unchanged. The graph must not gain execution authority from text in a report. No request may begin after the configured call limit, making each invariant directly testable through observable failure states.

The fixed teaching policy starts with USD 100000 cash. Quantities are positive whole shares. Shorting is forbidden. A purchase may not leave one stock above 10% of portfolio equity. The price comes from research evidence; the operator cannot type a favorable execution price. The operator chooses quantity and approves it. A valid sell can reduce an owned position even when the remaining holding is still above the purchase cap; a sell beyond the holding is rejected. Hold and REVIEW do not produce a tradeable proposal.

Eight acceptance specifications cover the important behavior. AT-01 exports and replays a complete package in a new process, then tests an incomplete package. AT-02 checks source availability, cutoff dates and duplicate handling. AT-03 demonstrates a valid approved transaction and repeat execution. AT-04 covers the forbidden execution cases. AT-05 changes approved terms or current portfolio state before execution. AT-06 exercises the actual request limit and critical context preservation. AT-07 compares six paired research runs. AT-08 exercises the six CI gates and their failure paths.

The first plan and test approval preceded the first recorded implementation event. The revision approval likewise preceded its first source edit. Gate 1 checks both sequences against the approval artifacts and raw session events.

The most useful negative cases correspond to plausible business failures. For example, approving 100 shares at USD 100 in an empty USD 100000 account reaches the cap exactly. An order for 101 shares must fail. However, those two tests alone cannot establish a total-position invariant. The review therefore adds a purchase after an existing position. That example distinguishes a correct holdings cap from an implementation that limits only the latest ticket.

Requirement volatility was controlled by keeping the feature scope fixed while clarifying ambiguous semantics. The project did not add a web application, extra analyst families or brokerage integration during implementation. The significant clarifications were that no-shorting permits valid sales, the cap applies to total holdings, approval includes quantity and evidence identity, and compact must affect actual per-agent inputs. Those clarifications are recorded in ADR-002 and the defect diary. They arose from reading the implementation against the approved behavior.

## 4. Architecture and authority boundaries

The selected architecture adds application-owned seams around the real graph. Three candidates were compared: broad modification of upstream internals, an application extension, and a replacement demonstration graph. The evaluation considered preservation of baseline behavior, deterministic authority, evidence coverage, delivery scope and maintenance. The application extension received the strongest design score because it preserves the real AI system while keeping the new transaction policy outside it.

The architecture has a clear flow. The operator invokes the CLI. ResearchRunner assembles a configured graph and a run recorder. The graph consumes market/news evidence and produces research state. EvidencePackIO saves the material needed for inspection and replay. A completed tradeable result can create a pending proposal. The operator reviews exact terms. Policy evaluates the current ledger. Storage applies a permitted transaction atomically and records its provenance.

```mermaid
flowchart TD
    A[Operator request] --> B[ResearchRunner]
    C[Frozen identity, prices and news] --> B
    B --> D[Real TradingAgents graph]
    D --> E[Requests, responses, usage and final state]
    E --> F[Portable evidence package]
    F --> G[Zero-network report replay]
    F --> H[Pending proposal]
    I[Operator exact-term approval] --> H
    H --> J[Current-ledger policy]
    J --> K[Paper transaction]
```

Module ownership follows these responsibilities. Models declares the persistent records. Config owns settings and teaching constants. Evidence captures calls and packages them. Graph_adapter owns the narrow integration with upstream. Context owns assembly and compaction. Budget owns request accounting. Review owns proposal transitions, while policy owns deterministic business decisions. Storage owns SQLite persistence. Replay reconstructs saved outputs, and the CLI exposes these capabilities to the operator.

The distinction between policy and storage is important. Policy decides whether the proposed state change is permitted. Storage records that approved change and its result. Neither module asks a model for permission. The graph's available tools contain research capabilities, and no tool grants approval or mutates the ledger. A sentence inside a model report requesting a policy bypass remains text; it is never interpreted as an operator command.

Approval refers to exact content. A fingerprint is appropriate for this purpose because it detects a changed combination of material evidence and trade terms. The fingerprint does not replace ordinary release or schema versions. After approval, changing quantity or price requires another review. A transaction also rechecks current cash and holdings because an earlier approved action may have changed the portfolio. These checks protect different boundaries: exact-content binding protects the user's decision, and current-state evaluation protects the portfolio invariant.

The REVIEW_REQUIRED state is recoverable. The first implementation correctly refused an unapproved execution but then prevented approval after entering the recovery state. That would leave the operator with a safe failure and no practical path forward. The corrected state machine allows the operator to inspect and approve the current terms. Completed and rejected proposals retain their explicit business meaning. The state-machine tests cover recovery rather than merely asserting that an error occurs.

Research and ledger memory have separate purposes. Upstream memory supports reflection on earlier decisions. The paper ledger represents approved positions and cash. Capturing the memory used in a research run makes that run inspectable, but a memory entry cannot authorize a transaction. Each evaluation process uses its own application home so experimental state cannot leak between cases. The storage model targets single-operator local CLI execution with isolated per-run application directories.

## 5. Evidence capture, replay and fixed inputs

Evidence capture begins at the real boundaries of the system. Model callbacks can record messages, returned content and reported usage. Tool callbacks can capture arguments and results. They do not automatically observe every data read. Source inspection identified identity resolution and return-history paths that bypass ordinary tool calls. The application subclass explicitly records or freezes these paths, closing a material gap in evidence completeness.

A package contains a manifest, material input snapshot, event stream, call records, usage summary and terminal state. It can include the proposal and presentation metadata. Completion is a structural claim about required records being present and parseable. A package missing a required record must fail replay rather than silently inventing it. Failed research still retains diagnostic evidence, but its incomplete status cannot become an approved recommendation.

Replay reads saved state and reconstructs the reports and structured decision. It does not ask a language model to recreate previous prose. The same package therefore gives an inspectable report even when the API is unavailable. Display timestamps may differ because they describe the reconstruction, while the decision and policy-relevant fields remain stable. The acceptance test starts replay in a fresh process and blocks external access to establish the intended dependency boundary.

A controlled rerun has a different contract. It executes the full research graph again, using fixed non-LLM data. Different context may lead the model to request a different indicator window or select a different valid tool argument. An exact lookup table of old tool calls would answer only the original transcript and return missing data for another valid request. That behavior could confound the comparison. ## 6. Context engineering and request budgets

The context design has six layers. Instrument identity establishes the subject. Standing constraints establish the analysis cutoff and advisory boundary. Retrieved knowledge supplies market and news evidence. Conversation history carries earlier arguments. Structured state supports continuation. The current task tells a specific role what it must produce. These layers are explicit because compression should remove redundancy without losing the task's controlling facts.

The assembly pipeline first filters evidence for eligibility. It then removes repeated material in compact mode, prioritizes essential content and applies a context budget. After compaction, it re-injects critical constraints. Symbol, analysis date, evidence price, source identity and the current task remain visible. Older discussion may be shortened when it repeats facts already present. The compact strategy also requests concise role responses to reduce repeated prose propagated to later roles.

Both arms execute the same selected upstream roles and model settings, with baseline passing the unmodified upstream prompt history and compact applying message deduplication and concise-output rules. The comparison therefore measures a context strategy rather than an architectural reduction in work. Both the input and output sides of provider usage are reported because concise output can affect later input size as well as the current response.

The first generated context implementation focused on past memory. That was a plausible local interpretation of compaction, and its unit tests could demonstrate deduplication. It would provide little benefit in six fresh cases with little memory. The review identified this mismatch before claiming an improvement and directed OpenCode to transform actual per-agent messages. This intervention illustrates why workload analysis matters: a correct local utility can fail to address the dominant cost of the application.

The request budget is an operational constraint. The counter must be checked before a real request starts. Merely recording an exceeded budget after a response would still spend the next call. Callback behavior also matters because some frameworks swallow callback exceptions, and structured-output fallbacks may retry a failed call. The acceptance test therefore exercises the invocation boundary with a fake provider and attempts one call beyond the configured limit.

A budget-stopped run keeps the evidence collected so far and records a distinct terminal outcome. It does not claim completion and does not create a tradeable proposal. A legitimate run that completes on its final allowed call should remain completed; reaching the numeric limit alone is not proof that another request was blocked. This distinction makes stop reasons useful for both the user and the evaluation.

Per-call output limits use the provider parameter contract, while character heuristics guide local context selection. All reported cost comparisons use provider token metadata, with judge usage recorded separately from application runs.

The complete-input budget is enforced immediately before every plain, tool-bound and structured provider invocation. It uses a conservative UTF-8 byte-based estimate with message overhead. The trigger is 72,000 units and the hard ceiling is 96,000. Compaction retains system constraints, the current task and factual evidence, including complete tool-call/result pairs. If essential content still exceeds the ceiling, the run stops and records context_budget_exhausted. The estimate controls admission; provider metadata measures actual token use.

## 9. Supervised process and improvements

The process began with course-document analysis and existing-source inspection. Requirements and acceptance examples were written before implementation. The initial approved slice connected evidence, review and a paper ledger so there was an early end-to-end workflow. This reduced integration uncertainty before adding the live experiment. The project then used measured failures and code review to choose the next changes.

OpenCode's first session generated the application and tests. Its raw record includes implementation attempts, test failures and corrections. The coordinating review examined business contracts instead of relying entirely on the agent's success statement. The review caught the difference between a ticket cap and total holdings, the omission of shares from approval binding, and the unintended rejection of all sales. It also noticed that an empty-memory compaction example could pass while delivering no useful savings on the planned workload.

The first session continued cleanup after its offline milestone. The coordinator ended that session and opened a shorter, focused live-evaluation session. This preserved the useful source changes and reduced the cost of repeatedly carrying a large context. The second prompt named the precise defects, fixed corpus, adapter behavior and required live commands. It did not ask the agent to revisit the entire project or produce another broad plan.

Work was divided by ownership to avoid conflicting edits. The core OpenCode session handled application and tests. A separate OpenCode session handled CI scripts and schema. Documentation was maintained alongside the source, and a video workflow captured actual CLI commands in an isolated demo home. The remote repository work waited for a concrete local deliverable. This parallel structure used the API waiting time productively while keeping each code owner bounded.

Defect trends are described from actual observations rather than invented issue counts. Early failures concerned packaging, context bookkeeping and a recovery transition. Later review findings concerned business semantics and experimental validity. That progression suggests the implementation became mechanically runnable before it fully represented the approved contracts. The improvement was to move from broad test counts to a smaller number of discriminating examples at each authority boundary.

Ambiguity resolution is explicit. “No shorting” was interpreted as allowing a sell up to owned shares. “Ten percent position” constrains total holdings after a buy, while a valid sale can reduce an overweight holding. “Approval” covers quantity and material evidence. “Replay” reconstructs a saved result, while “rerun” regenerates one from fixed input. “Token reduction” refers to actual provider usage. These definitions are reflected in the requirements, ADRs and tests so later maintenance does not have to reconstruct the reasoning from a conversation.

Artifacts co-evolved through the trace matrix. A change to the holdings interpretation affected the policy owner, approval decision, test examples and defect diary. A change to the context strategy affected ADR-001, the runtime adapter and evaluation method. Updating the JSON schema ensured that automated validation checked the committed requirements registry, while the AI-use gate verified that session logs stayed synchronized with source and prompt paths.

Governance records specify what an authorized change may do. Test logs and provider metadata show what ran, and GitHub responses show whether the server enforced its release policy.

## 10. Scope and further work

Research Desk is a single-operator paper application. A networked deployment would require authenticated identities and a separate concurrency design. Broker execution and transaction costs are outside the implemented workflow.

The current six-case corpus measures regression behavior on fixed evidence. The judge's raw explanations remain part of the quality record, alongside deterministic facts. Broader financial coverage would require additional reserved cases and repeated trials. Provider or upstream changes reopen the adapter contract and trigger a new complete evaluation.

The context study in Section 9 examines a defined maintenance task. Future development can repeat that comparison across larger architectural changes to measure how context selection affects both token cost and defect rates.

## 11. Individual reflections

### Alfa

Requirements engineering on an agentic codebase succeeds or fails on how tightly natural-language rules constrain edge-case states. During the initial specification of the 23-item registry and MoSCoW priorities, prose descriptions of trading safety appeared unambiguous. Early implementation review revealed that short phrases hid divergent interpretations that passing unit tests did not immediately expose. A ten percent position limit initially passed verification when checked against a single order ticket of 100 shares at USD 100 in a USD 100000 account, yet that check failed to prevent a second purchase from pushing cumulative equity exposure above the cap. Similarly, a blanket prohibition on short selling was first realized in code as a total ban on sell orders, which blocked legitimate position reductions, and the initial approval fingerprint bound instrument symbol and evidence price while omitting operator-selected share quantity. Resolving these gaps required updating ADR-002 and linking each requirement to discriminating negative acceptance tests in AT-04 and AT-05. The held-out META compact run provided another requirements lesson when the report used the ticker and short name while omitting the full legal string Meta Platforms, Inc., leaving 59 of 60 checks passing under QUALITY-001 despite strong semantic scores. Separating Must invariants from Should performance targets established a stable decision framework before live metrics arrived, ensuring that a 45.73% token reduction could not excuse a missing identity field or relax a ledger rule. For future review practice, specification work will pair every numeric invariant with multi-step state-transition counterexamples before code generation starts. Requirements involving generated prose will separate deterministic format contracts, such as exact legal entity strings and evidence prices, from rubric-based semantic evaluation, ensuring that schema validators verify structural identity fields directly at the output boundary. The revised scope also makes five substantial increments visible across the team. Evidence portability and approved execution establish user-facing behavior. Context efficiency, bounded inputs and release-quality checks supply separate measurable engineering requirements. Keeping each increment attached to an owner and a fit criterion makes the contribution table useful during review, without treating document counts as a measure of engineering effort.

### Bravo

Designing the extension seams and context budget around TradingAgents v0.4.0 highlighted the difference between a locally valid utility and a workload-effective architecture. Evaluating three architectural options led to wrapping the unmodified upstream graph with application-owned adapters rather than rewriting core agent nodes or substituting a toy pipeline. That choice preserved upstream analyst roles and structured state propagation while isolating context assembly and call accounting in dedicated modules. The first context compaction implementation demonstrated a classic architectural pitfall: the code deduplicated past reflection memory and passed isolated unit tests, yet fresh evaluation runs across the six equity cases began with almost no prior memory. Workload inspection showed that dominant token consumption came from repeated per-agent prompt history and verbose intermediate responses passing across the graph. Redirecting compaction to filter active message layers while re-injecting standing constraints, ticker identity, analysis cutoff, and task instructions at every request boundary made the optimization effective on actual runs and corrected the initial zero-citation failure recorded in prompt version research-desk-0.1.1. Request budgeting exposed a similar boundary issue, because checking a counter after a response arrives or relying on framework callbacks that swallow exceptions cannot stop an over-budget API call or a structured-output retry. Enforcing the budget check immediately prior to provider invocation allowed the max_calls=1 run to halt cleanly at 2273 tokens with a budget_stopped status while preserving diagnostic state. In future architecture reviews, component designs will be validated against empirical token and call profiles from a pilot trace prior to full implementation, and every resource cap or standing prompt constraint will be verified at the lowest-level provider adapter boundary rather than assumed to survive framework propagation. A further design distinction separates call limits from per-request input size. Bounding complete prompt payloads requires accounting for tool responses and standing instructions while preserving assistant-to-tool call linkages during compaction. The ADR-004 request-boundary implementation therefore verifies oversized mandatory evidence and paired tool identifiers directly in unit tests, complementing call-count budgeting with a deterministic input ceiling.

### Charlie

Building the evidence capture pipeline and proposal state machine showed that deterministic authority depends on controlling every data path and transition edge around a stochastic model. Relying solely on standard LangChain model and tool callbacks initially left blind spots because upstream instrument resolution and return-history reads accessed data outside ordinary tool invocations. Subclassing the adapter to capture and freeze those direct reads closed the completeness gap so exported ZIP packages could replay in fresh processes with zero network calls in under 0.82 seconds. Real execution during the initial AAPL pilot exposed two boundary defects at export time: unserialized LangChain message objects in the terminal state broke JSON packaging, and an overly broad credential-redaction regex stripped numeric token usage fields alongside secret keys. Fixing serialization at the capture boundary and scoping redaction strictly to authentication strings preserved complete audit data without leaking credentials. On the transaction side, separating the Review module from Policy and SQLite Storage ensured that model text could never mutate the ledger, while cryptographic fingerprinting tied operator approval to the exact combination of evidence package, direction, price, and share quantity. State-machine testing also revealed that safety requires recoverability: when an unapproved or modified proposal entered REVIEW_REQUIRED, the earliest transition table locked the record instead of permitting the operator to inspect and approve the updated terms. Subsequent defect analysis also showed that rejected proposals must preserve an explicit terminal status if execution is attempted. Reproducing the `reject -> execute -> approve` sequence with an isolated mock store demonstrated that `execute` previously transitioned rejected records into `REVIEW_REQUIRED`, allowing a subsequent approval to succeed. Locking `REJECTED` as a terminal state in ADR-004 and verifying the multi-step sequence in `test_revision_contracts.py` closed this transition gap. In future engineering reviews, state-machine verification will require a complete transition matrix covering both recovery and terminal rejection paths before live evaluation begins. The repaired test also checks that rejection leaves ledger reads and transaction writes untouched. This makes the authority boundary observable through both state and storage effects.

### Delta

Structuring the three-tier verification suite and executing the twelve-run evaluation matrix demonstrated that measurement pipelines require the same debugging rigor as application code. Offline verification progressed from 47 initial tests to 98 application tests alongside 649 passing upstream checks, using socket-blocked subprocesses and controlled fixtures to verify replay isolation and the ten percent equity cap. When evaluation moved to live DeepSeek runs across the two development cases and four held-out cases, two distinct failures emerged in the evaluation harness itself. First, the initial AAPL and MSFT runs achieved a 36.07% token savings but scored zero on citation validity because standing grounding rules did not reach downstream roles; archiving that failed batch under evaluation/development-initial and updating the request adapter resolved the defect before opening the held-out split. Second, during final scoring, the convenience input projection passed to the independent judge retained only the last tool output when an agent invoked the same tool name multiple times, hiding earlier observations that remained intact in the canonical event stream. Rebuilding the judge input from the complete recorded event stream and re-running all twelve judgments restored observation fidelity without altering any model output or rubric threshold, while keeping both sets of judge transcripts and their 241278 and 236462 token costs transparent. Even with a 0.9000 compact support mean, the MSFT compact report divided share price by single-quarter EPS to state a trailing P/E ratio while still receiving a 0.9 support score from the LLM judge. Future evaluation reviews will audit data projections against canonical event logs before invoking judge models and will pair LLM rubrics with deterministic domain checks for period alignment and financial formulas. Release evaluation also needs a link to the implementation being assessed. A successful archived score becomes stale when the prompt or evaluator changes. Binding each fresh run and its judgment to the evaluated source makes this relationship explicit. Unit cases for missing results and stale evidence can then verify the acceptance mechanism without consuming additional model calls or replacing a real experiment.

### Echo

Managing continuous integration, packaging, and repository governance demonstrated that automated enforcement is only as reliable as the environment and schemas backing it. Early integration exposed a basic packaging flaw when the generated src-layout omitted package discovery settings in pyproject.toml, preventing the research-desk CLI from importing until the build configuration was repaired and tested in an isolated environment. Designing the six local verification gates required coupling documentation artifacts directly to executable validators across test chronology, static typing and linting, requirements schema compliance, offline semantic replay, full regression suites, and AI-use log synchronization. The initial unified gate run archived in evaluation/ci-initial proved the value of testing the validators themselves: static validation failed on an unresolvable external JSON Schema URI when run offline, and the AI-use gate missed a test directory marker. Fixing those defects and running six deliberate negative probes confirmed that the local pipeline rejected bad chronology, unapproved safety edits, and schema violations in the saved local execution. Release execution then highlighted the boundary between local reproducibility and hosted platform governance. Although the private GitHub repository received the verified commit history and signed upstream v0.4.0 tag, the initial remote GitHub Actions runs were blocked prior to job execution by account billing limits, and private repository branch protection returned HTTP 403 under the current plan. Recording the exact API responses and desired protection payload in evaluation/github preserved an honest audit trail for D7 and GOV-004. In future release workflows, repository hosting constraints, runners, and branch-protection permissions will be probed with an early actual workflow run at project initialization, and all schema validators will be forced to run under strict network isolation from day one. Making the repository public enabled full hosted enforcement of the six CI gates and branch protection rules on `main`. Both the initial public workflow run and the ADR-004 revision pull request (PR #1) passed all six cloud checks under the consolidated `ci.yml` pipeline. The pull request now awaits independent code-owner approval prior to merge, separating automated release verification from human authorization.

# ADR-001: Extend the existing graph through application-owned seams

Status: accepted by leo, 2026-08-31. Requirements: FR-001 through FR-003, INV-001, INV-002. The concrete plan and tests were approved at 12:05:17.791955 UTC before OpenCode's first implementation event at 12:06:32.695 UTC.

## Context and alternatives

TradingAgents v0.4.0 already provides multi-agent research, structured decisions, date-aware memory, checkpointing and price validation. The missing product workflow is portable evidence followed by explicit approval and paper execution. A complete graph rewrite would discard tested domain behavior and make the optimization baseline incomparable. Editing every upstream prompt and tool would distribute application-specific policy across many owners. A narrow application extension keeps the experimental boundary visible.

Candidate A modifies the entire graph and shared vendors. Candidate B subclasses/composes the existing graph and implements policy outside it. Candidate C builds a small new agent demo. The evaluation table selects B because it preserves genuine AI integration while keeping deterministic authority isolated. The original graph's full selected role sequence is retained in both experimental arms.

## Context layers and assembly

Layer1 identifies the instrument and analysis cutoff. Layer2 states standing constraints: use available evidence, retain source identity, distinguish unknown facts and keep execution advisory. Layer3 supplies frozen market/history/news knowledge. Layer4 holds current discussion and retrieved past context. Layer5 preserves resumable structured state. Layer6 gives the current agent task and expected output.

The assembly order is eligibility filtering, duplicate removal in compact mode, prioritization, budget accounting, compaction and final constraint reinjection. Baseline preserves original substantive prompt input. Compact can remove repeated paragraphs or shorten older discussion, while retaining symbol, date, price evidence, source IDs and current task. It also requests concise role output to reduce repeated prose passed to later agents. Fresh six-case runs have little past memory, so compact must apply to actual per-agent messages; changing only a memory string would leave the dominant token cost unchanged.

The call budget is configured for the experiment. Per-call maximum output bounds use the provider's existing max_tokens contract. Character estimates may guide context assembly but never replace provider-reported token usage. The model adapter checks before starting a request; a structured-output retry cannot create an extra request after the budget is exhausted. Critical constraints are re-injected after compaction. Factual quality is evaluated independently of brevity.

## Consequences and reopening conditions

Evidence packs contain prompts and responses and are larger than ordinary reports. Replay is fast because it reconstructs captured state; controlled reruns call the model and remain stochastic. The frozen provider must answer valid parameter variations from data, because an exact tool-transcript lookup would bias the comparison when compact changes tool arguments.

The approval boundary stays outside all model tools. The extension retains responsibility for current-ledger checks even if upstream research changes. Reopen this ADR if an upstream public interface cannot expose a material external read, if multiuser concurrency is added, or if compact cannot satisfy factual constraints without discarding agent roles. No such need justifies silently replacing the baseline.

## Affected paths

The accepted application scope includes `src/research_desk/config.py`, `graph_adapter.py`, `budget.py`, `evidence.py`, `context.py`, `models.py`, `replay.py`, `report.py`, `cli.py` and the application-owned `src/research_desk/eval/` adapters. `pyproject.toml` exposes the installed extension. These paths implement the already approved evidence, research-context and runtime-budget boundaries. The deterministic approval and ledger changes are specified more precisely in ADR-002. No upstream vendor implementation is replaced.

## Development correction within the accepted boundary

The initial two-case experiment established token reduction but failed citation acceptance. The initial past_context alone did not reach downstream roles, so the common evidence policy is now attached to every real model request in both arms through a plain delegate. Tool binding and structured output compose a LangChain Runnable preprocessor with the real client; they preserve the real returned messages and tool-call identities. Baseline substantive history stays unchanged. Compact retains its declared concise-output target. Runtime prompt version0.1.1 records this source-grounding correction, and the0.1.0 snapshot and original development outputs remain available. ADR-004 adds a 96,000-unit whole-input cap and a 72,000-unit compaction trigger. Units are a conservative UTF-8 byte bound with message/tool-call overhead. These values are defined once in ResearchDeskSettings defaults. The delegate preserves mandatory evidence and tool-message pairs. If required input cannot fit, it stops before model invocation. # ADR-002: Bind approval to exact terms and cap total holdings

Status: accepted by leo during implementation review, 2026-08-31. Requirements: FR-002, INV-001, INV-002. This clarifies the approved policy rather than adding a new feature.

The source of truth for completion is the final offline test log, not this acceptance decision.

The10% concentration test applies when buying. A valid sale can reduce a position that became overweight through a price rise, even when the remaining holding is still above10%. Such a sale cannot create a short position. Rejecting risk-reducing sales would add an unapproved constraint to the original policy. The direct boundary example holds100 shares bought at100 with90000 cash, marks them at200, and permits a sale of10 shares; it leaves90000 +2000 cash and90 shares.

# ADR-004: Bound context and gate release quality

## Drivers and decision

# ADR-001 Appendix: Evidence pack format and offline replay

Status: accepted appendix to `001-application-extension.md` (2026-08-31, decided by leo). Context: F1. The application-extension ADR remains the authoritative architectural decision; this appendix specifies its package representation.

## Decision

An evidence pack is a self-contained directory (or a ZIP of one) with a fixed
set of JSON/JSONL files: `manifest.json`, `input.json`, `events.jsonl`,
`final_state.json`, `usage.json`, `calls.json`, optional `proposal.json`, and
`meta.json`. `complete` is only set when every required file is present and
parses. Import validates required files and fails loudly on a missing record.

Replay rebuilds the report tree from `final_state`, derives the signal with the
same deterministic heuristic the graph uses (`SignalProcessor`), and reports
the deterministic policy bounds for the proposal against a ledger. Replay never
constructs an LLM client.

## Why

- The final graph state plus the captured tool data are the *material* needed
  to rebuild reports and policy outputs with zero external calls; LLM re-output
  is not needed and would violate "no network on replay".
- Complete/incomplete is a structural property (required files) so a partial
  pack cannot silently replay a wrong decision.
- JSONL events keep the log append-friendly and streamable.

## Consequences

- Evidence packs can be large (they keep full prompts/responses for provenance).
- Replay is deterministic for the signal and policy; the *report timestamps*
  are display metadata and intentionally differ from the original run.
